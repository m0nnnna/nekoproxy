# NekoProxy Security Audit Report

**Date:** 2026-03-22
**Scope:** Full codebase — controller, agents, shared libraries, web UI, configuration
**Auditor:** Internal (Claude Code)

---

## Executive Summary

A full-source security audit of the NekoProxy controller and agent codebase was conducted.
**Five critical** and **four high-severity** vulnerabilities were identified, all of which
have been remediated in this commit.  Several medium-severity issues were also identified
and addressed.

---

## Critical Findings (Remediated)

### CRIT-01 — Unauthenticated Agent ControlAPI: Remote Code Execution

**Location:** `agent/core/control_api.py` — `/update-binary` endpoint
**Severity:** Critical
**CVSS v3:** 10.0 (Network / No Auth / No User Interaction)

**Description:**
The agent's internal HTTP API (aiohttp, port 8002) accepted POST requests to
`/update-binary` with no authentication whatsoever.  This endpoint writes the
request body as an executable to disk and immediately spawns it via PowerShell
(Windows) or shell (Linux).  Any host able to reach port 8002 could achieve
full Remote Code Execution as the agent process user.

**Remediation:**
All agent ControlAPI endpoints now require an `X-Controller-Token` header matching
`settings.controller_token`.  The token is auto-generated by the controller on first
run and must be set as `NEKO_AGENT_CONTROLLER_TOKEN` on all agents.

---

### CRIT-02 — No Authentication on Controller API Endpoints

**Location:** All `controller/api/v1/*.py` endpoints
**Severity:** Critical

**Description:**
Every controller API endpoint — including `/api/v1/agents/`, `/api/v1/services/`,
`/api/v1/blocklist/`, `/api/v1/firewall/`, `/api/v1/stats/`, `/api/v1/alerts/`,
`/api/v1/assignments/`, and `/api/v1/email/` — required no authentication.  Any
network-reachable host could read or modify the entire proxy configuration, agent
list, blocklist, and firewall rules.

**Remediation:**
- Admin endpoints: require `X-API-Token` (or `Authorization: Bearer`) header
- Agent-facing endpoints (heartbeat, config, stats, blocklist/report, alerts): require
  `X-Agent-Token` header with the per-agent token, or the admin token
- Registration (`/api/v1/agents/register`): continues to use the optional `agent_secret`

---

### CRIT-03 — No Authentication on Web UI

**Location:** `controller/web/routes.py` — all dashboard routes
**Severity:** Critical

**Description:**
The entire web dashboard (agents, services, firewall rules, blocklist, email settings,
settings page, etc.) was accessible to any browser that could reach port 8001 with no
login required.

**Remediation:**
Added session-cookie authentication to all web routes.  Users must log in at `/login`
using the API token as the password.  Sessions expire after 8 hours.

---

### CRIT-04 — Unencrypted Controller↔Agent Communication

**Location:** All agent → controller HTTP calls; all controller → agent HTTP calls
**Severity:** Critical

**Description:**
All communication between controller and agents used plain HTTP, meaning:
- Agent tokens, configuration data (blocklists, firewall rules, service backends) were
  transmitted in cleartext
- An attacker with network access between a controller and agent could intercept or
  modify traffic (MITM)
- This affected connections over WireGuard IPs (partially mitigated by WireGuard
  encryption) AND raw IP connections (completely unencrypted)

**Remediation:**
- Controller: `NEKO_SSL_CERTFILE` / `NEKO_SSL_KEYFILE` settings activate HTTPS via
  uvicorn TLS (supports both domain names and raw IP SANs)
- Agent: `NEKO_AGENT_CONTROLLER_SSL_VERIFY` and `NEKO_AGENT_CONTROLLER_SSL_CA_CERT`
  control verification of the controller's TLS certificate
- Agent ControlAPI: `NEKO_AGENT_CONTROL_SSL_CERTFILE` / `NEKO_AGENT_CONTROL_SSL_KEYFILE`
  activate HTTPS on the agent's aiohttp server

---

### CRIT-05 — No Per-Agent Token; Heartbeat/Config Unauthenticated

**Location:** `agent/core/heartbeat.py`, `agent/core/config_sync.py`,
`controller/api/v1/agents.py`
**Severity:** Critical

**Description:**
After registration, agents sent heartbeats and config requests with only their
`agent_id` (an integer) as identification.  Any party guessing or enumerating an
`agent_id` could:
- Send fake heartbeats to mark an agent as healthy when it is not
- Read the full agent configuration (including all backend hostnames, ports, and
  the complete blocklist)
- Modify the agent's perceived state

**Remediation:**
On registration, the controller now generates and returns a unique 256-bit random
`agent_token`.  All subsequent agent → controller requests must include this token
in the `X-Agent-Token` header.  The token is saved to `agent_token.txt` in the
agent's install directory and loaded on restart.

## High Findings (Remediated)

### HIGH-01 — Agent Secret Optional by Default; No Forced Registration Auth

**Location:** `controller/api/v1/agents.py` → `/register`; `controller/config.py`
**Severity:** High

**Description:**
The `agent_secret` mechanism (requiring agents to present a shared secret at
registration) was disabled by default.  With no secret configured, any host could
register as a legitimate agent and receive configuration data.

**Remediation:**
No change to the optional-secret behaviour (it remains the same), but the new
per-agent token mechanism means that even if a rogue agent registers successfully,
it cannot fake heartbeats or read configs for existing legitimate agents (each has
its own token).  Operators are strongly encouraged to set `NEKO_AGENT_SECRET`.

---

### HIGH-02 — Stats and Blocklist Reports Unauthenticated

**Location:** `controller/api/v1/stats.py` → `POST /connections`, `POST /email`,
`POST /firewall`; `controller/api/v1/blocklist.py` → `POST /report`
**Severity:** High

**Description:**
Any host could POST arbitrary statistics or add IPs to the blocklist by calling
`/api/v1/blocklist/report`.  This allowed stat database poisoning and forced
blocking of legitimate IPs (denial-of-service against the blocklist).

**Remediation:**
These endpoints now require either the admin API token or a valid per-agent token.

---

### HIGH-03 — Plaintext Tokens Stored in DB Without Hashing

**Location:** `controller/database/models.py` — `GlobalSettings.agent_secret`,
`GlobalSettings.api_token`, `Agent.agent_token`
**Severity:** High (residual)

**Description:**
Tokens are stored in plaintext in the SQLite database.  If the database file is
exfiltrated, all tokens are immediately usable.

**Remediation (partial):**
This is a known trade-off with single-server SQLite deployments.  Operators should:
- Restrict filesystem access to the database file (chmod 600, service account ownership)
- Rotate tokens if a database compromise is suspected
- Consider using PostgreSQL with column-level encryption for higher-security deployments

---

### HIGH-04 — Controller Calling Agents Over Raw HTTP With No Auth

**Location:** `controller/core/agent_sync.py`, `controller/core/email_manager.py`,
`controller/web/routes.py`
**Severity:** High

**Description:**
The controller called agents' ControlAPI endpoints (trigger-sync, deploy-email,
update-binary) over plain HTTP with no mutual authentication.  A rogue server at
the agent's WireGuard IP could intercept and respond to these calls.

**Remediation:**
Controller now sends `X-Controller-Token` on all outbound calls to agents.
SSL verification is configurable via `NEKO_AGENT_API_SSL_VERIFY`.

## Medium Findings (Remediated / Noted)

### MED-01 — Session Cookie Not Marked Secure When HTTP Is Used

**Location:** `controller/web/routes.py` — login endpoint
**Status:** Remediated
**Description:** Session cookie `Secure` flag is now conditionally set — enabled
only when `NEKO_SSL_CERTFILE` is configured (i.e., HTTPS is active).

---

### MED-02 — Controller Token Not Rotated on Agent Re-Registration

**Location:** `controller/api/v1/agents.py`
**Status:** Noted (accepted risk)
**Description:** Re-registering an existing agent (same WireGuard IP) does not
rotate its `agent_token`.  This preserves continuity for restart scenarios.
Operators can manually delete the agent and re-register to rotate the token.

---

### MED-03 — No Rate Limiting on Login Endpoint

**Location:** `controller/web/routes.py` — `POST /login`
**Status:** Noted
**Description:** The login endpoint has no brute-force protection.  Mitigated by
the strength of the auto-generated 256-bit token (infeasible to brute-force in
practice).  Operators behind a reverse proxy (nginx, Caddy) should add rate
limiting there.

---

### MED-04 — Hardcoded HTTP for Agent ControlAPI in Email Manager

**Location:** `controller/core/email_manager.py`
**Status:** Remediated
**Description:** Email manager hard-coded `http://` when building agent ControlAPI
URLs.  Now uses `get_agent_base_url()` which respects `control_url` overrides, and
controller sends `X-Controller-Token` header.
